# TRACE fixture investigation — 9 October 2026

The 487 changed membership cells split into two mechanisms: 466 numerical
boundary classifications and 21 substantive legacy footprint changes caused by
contradiction removal amplifying small projection differences. All 21 substantive
changes were reproduced with frozen coordinates on one MATLAB runtime. This is
not evidence of repeat-run instability: the two new complete exports remain
byte-identical across all 423 artifacts.

## Sources and method

Compared the approved MATLAB `98a01ac` / R2026a Update 4 / MACA64 bundle with the
candidate from MATLAB `929acfd` / R2026a Update 5 / GLNXA64, generated by Python
repository commit `9bdc37a`. Approved fixtures and pins were not changed.

For each changed membership cell, reconstructed the 2D polygon union (including
holes) or the 3D boundary triangles and measured the query's distance to both
old and new boundaries. Compared 2D boundary connectivity by mapping vertices to
training-point indices, and compared native 3D face connectivity directly.
The `1e-10` distance used to group diagnostic cases is not a production tolerance
or a change to fixture validation; actual TRACE3 distances are below `1.1e-14`.

Then replayed `TRACE_legacy` on the frozen old and new training projections using
identical labels, options, seed 42 and current MATLAB with one computation thread.
Repeated with contradiction removal off and on. An isolated instrumented copy
logged overlap counts and purity decisions. Production MATLAB/Python code was
not modified.

## Boundary cases: all TRACE3 membership changes

| Variant | Changed cells | Boundary cases | Maximum distance to either boundary |
| --- | ---: | ---: | ---: |
| Default TRACE3 | 44 | 44 | 9.53e-15 |
| TRACE3, PYTHIA skipped | 198 | 198 | 1.05e-14 |
| Standard analytic 3D | 172 | 172 | 1.09e-14 |
| Legacy | 73 | 52 | The other 21 are substantive, described below |

Both 2D TRACE3 variants retain the same boundary edges, and the 3D variant retains
the same boundary faces. No change in connectivity explains these TRACE3 flips.
Numerical coordinates do change: the 2D projection changes at about `1e-6`, while
analytic 3D changes only at about `1e-14`. In either case, the flipped points lie
on the corresponding boundary to floating-point precision.

Most of these queries repeat training instances: 44/44 default, 197/198 skipped,
171/172 3D and 52/52 legacy boundary cells have training-set instance names.
In the new bundle, the same named instance's exported training and explore
coordinates can differ by approximately `1.1e-14`. Thus a mathematically boundary
point can land just outside the fitted footprint during inference.

This is sensitivity of exact inside/outside predicates at the boundary, rather
than a material change to TRACE3's footprint shape. It still changes reported
membership and density/purity, so those bits should not simply be declared equal.

## Legacy: small coordinate changes trigger different trimming decisions

The 21 non-boundary changes occur in best-J48 (4 cells) and best-Random-Forest
(17 cells). The implementation of `TRACE_legacy` between the two source revisions
differs only in documentation. It consumes the true best-algorithm labels `P`,
not PYTHIA's SVM selections; `P` and the other label inputs are unchanged.

Controlled replays reproduce the following original footprint areas:

| Footprint | Old-coordinate replay | New-coordinate replay |
| --- | ---: | ---: |
| Best J48 | 1.8414883719 | 1.6473962301 |
| Best KNN | 0.1150759053 | 0.1163184355 |
| Best Random Forest | 1.8470560842 | 1.5846840701 |

With contradiction removal disabled, the maximum old/new area difference across
all good/best footprints is only `6.44e-6`. With it enabled, it reaches `0.262372`.
The larger changes therefore arise during trimming, not from an SVM prediction
change or a new implementation of the legacy builder.

One captured decision is KNN versus Random Forest. On the old coordinates, the
overlap has one counted point: KNN purity 0 and Random Forest purity 1. On the new
coordinates it has two: both purities are 0.5. The old run trims the KNN footprint;
the new run follows the equal-purity branch and stops resolving that overlap.
Other overlap/iteration counts differ as the sequential trimming proceeds.
This is a discontinuity: small geometric changes alter integer counts, which
change a discrete branch and can remove or retain a substantial region.

Using each bundle's own query coordinates, the controlled replay reproduces all
21 substantive membership changes. The old-coordinate replay reproduces every
old membership bit. The new-coordinate CSV replay differs from the original
native export in 24 additional bits, all within `1.05e-14` of the boundary.
That last result also exposes sensitivity to CSV round trips; it does not explain
away the 21 substantive changes.

## Consequences for promotion

The investigation explains both mechanisms but does not justify automatically
promoting changed outputs or loosening all comparison tolerances.

1. Preserve full precision in the 2D diagnostic/export path as well as 3D. This
   avoids adding serialization perturbations, although native train/explore
   boundary sensitivity remains.
2. Establish a shared MATLAB/Python boundary policy, with targeted near-edge,
   near-face and repeated-instance tests. If a scale-aware boundary inclusion
   rule is adopted, apply it consistently to membership and metric counts.
3. Add a fixed-coordinate legacy contradiction regression around the overlap
   count/tie behavior. Decide explicitly whether historical exact decisions or
   robust geometric decisions are the intended contract before changing them.
4. Review candidate membership and summaries under that contract before promoting
   the full fixture bundle or closing #347.

Local evidence lives under `.cache/matlab-review-2026-10-09/trace-investigation/`:
`compare.py`, `changed-memberships.csv`, `geometry-comparison.csv`, `summary.json`,
the MATLAB replay/instrumentation scripts, saved native footprints and replay

## Agreed boundary policy implementation

Following review, the user selected an **explicit Euclidean distance tolerance,
with default zero**. The provisional epsilon-multiplier approach was discarded;
there is no automatic `64 * eps` policy in either implementation.

MATLAB PR #66 adds `opts.trace.boundaryTolerance`; Python PR #348 adds
`TraceOptions.boundary_tolerance` and accepts MATLAB's camel-case JSON spelling.
Both use the distance in projection-coordinate units, keep exact closed-boundary
semantics at zero, and include near-edge/near-face points only when the caller
supplies a positive distance. Hole interiors outside that distance stay excluded.
Geometry and area/volume are not buffered. The fitted value is persisted and
reused by prediction/rescoring, construction metrics and legacy trimming counts.
Older models without the field use zero. Query batches cannot scale the tolerance.

The implementations share an identical hand-labelled JSON contract covering holes,
faces, edges, corners, explicit distances, scaling/translation and singleton/batch
queries. Additional tests cover empty/disconnected geometry, invalid options,
persistence and the independent fixture validator. Python's full suite passed
1,119 tests; the final expanded boundary-focused suite passed 13 tests. Strict
mypy passed 92 files. MATLAB boundary/state/options/stage/compatibility regressions
passed, and an Octave 2D/3D compatibility smoke test passed. Both documentation
builds passed. A complete diagnostic export against the updated INIT branch
completed, with the approved fixture bundle untouched.

The exporter uses the fitted tolerance for membership, and writes 2D TRACE
coordinates/rings at full double precision. The validator honours a declared
3D tolerance independently; historical option records without it retain zero.

The legacy replay at zero preserves the previously observed area differences.
An explicitly supplied diagnostic tolerance of `1e-12` also leaves those larger
area differences in this case. This option establishes consistent semantics;
it is not a universal cure for discontinuous legacy trimming, and no positive
default or automatic fixture promotion is implied.
